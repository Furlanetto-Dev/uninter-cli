# The sidebar and the pane beside it

## TL;DR
- `components/sidebar.py` holds `Sidebar(OptionList)` with the six declarations `app.tcss` repeats today; `MateriaList` and `QuestaoList` subclass it.
- `components/pane.py` holds `DetailPane(Vertical)` with `height: 1fr; padding: 1 2`; `#detail` and `#prova-detail` become it.
- The four blocks leave `app.tcss`, which keeps only what is about one screen.
- The layout does not change: the same widths, borders and padding, moved from the stylesheet into the widgets.

A screen that wants this app's shape copies six lines of CSS today, which is how the prova screen got it. Part of [0016](0016-cli-components.md).

## Observed behaviour
- `MateriaList` and `#prova-questoes` carry `width: 44`, `height: 1fr`, `border: none`, `border-right: solid $panel`, `padding: 1 1`, `background: $surface` — the same six declarations in the same order, at lines 5 and 162 of `app.tcss`.
- `#detail` and `#prova-detail` carry `height: 1fr; padding: 1 2`, at lines 14 and 171.
- Both sidebars are `OptionList` subclasses, so one base class reaches both; the panes are plain `Vertical` containers.

## Decisions

### The widget carries its own look, in `DEFAULT_CSS`
A component that lives in `components/` and leaves its appearance in `app.tcss` is only half moved — the next screen would still have to know which block to paste. `DEFAULT_CSS` travels with the class, and `app.tcss` keeps the last word for anything one screen needs to bend, which is how `Screen.-debug.-short` already works.

### `Sidebar` is a base class, not a container to wrap around a list
`MateriaList` and `QuestaoList` are both `OptionList` subclasses with their own rows, messages and bindings. Subclassing keeps them one widget each; wrapping would add a node to the DOM and a `query_one` to every caller.

### `DetailPane` earns its module despite being two declarations
It is the other half of the shape: a screen picks `Sidebar` and `DetailPane` together, and having only one of them in `components/` is how the pair drifts apart again.

## Rejected
- **A CSS class such as `.sidebar` in `app.tcss`.** Still a stylesheet a new screen has to know about, and nothing stops it from being copied instead of used.
- **One `Layout` component that composes both.** The two screens differ in what sits beside the list — tabs and a debug panel on one, a scrolling body on the other — so the layout is not the shared part.

## What execution corrected
- **The `:focus` border had to move with the rest.** Textual ranks every user-CSS rule above every `DEFAULT_CSS` rule — `default_rules` is the first field of the specificity tuple — so the six declarations that beat `OptionList:focus` from `app.tcss` stopped beating it once they became a component default. `Sidebar` repeats the border under `&:focus`; removing that block and re-rendering brings Textual's tall border back, which is how it was found.
- `#prova-detail` lost its id along with its block, since nothing else named it. `#detail` keeps its own: `Screen.-debug.-short #detail` still needs it.
- The comparison now covers colour, not just characters. A CSS move can change nothing but the palette, so the harness compares each segment's style; the six views are identical under it.
